# PR 컨벤션 (작은 PR 정책)

사람이 실제로 읽을 수 있는 크기로 올린다. 코드가 많으면 리뷰가 형식적이 된다.

## 원칙
- 한 PR = 한 가지 변경. 기능·리팩터·포맷 정리를 섞지 않는다.
- 큰 기능은 계층별로 나눈다. 예: ① 모델·마이그레이션 → ② service + 테스트 → ③ API → ④ 화면.

## 상한
| 항목 | 상한 |
|---|---|
| 변경 라인(추가+삭제) | ~400줄 이하 |
| 변경 파일 수 | ~20개 이하 |

- 현재 CI가 없어 **리뷰어가 확인한다**. 넘으면 본문에 이유를 적는다(예: 프로젝트 뼈대 생성).
- 크기 계산 제외: `package-lock.json`, `frontend/dist/`, 자동 생성 파일.

## PR 본문 양식
```markdown
## 무엇을
(한두 줄 요약)

## 왜
(관련 문서: docs/spec/... 또는 docs/planning/...)

## 수용 기준 / 불변식 / 테스트
- 수용 기준:
- 불변식: (ai-code-trust.md 표의 번호 또는 새 항목)
- 테스트:

## 실행 · 확인 방법
(로컬에서 어떻게 띄우고 무엇을 눌러 보면 되는지)

## 검증
- [ ] backend: pytest, ruff check 통과
- [ ] frontend: npm run build, npm run lint 통과
- [ ] 별도 세션 우회 시도·보안 점검 (무엇을 확인했는지 한 줄)
```

## 리뷰
- **승인 1명 이상** 후 머지. 작성자 본인 머지는 승인 뒤에만.
- 분류기 계약·채팅 정책(`backend/app/services/`, `backend/app/classifier/`, `nlp/`)을 바꾸는 PR은 **웹 1명 + NLP 1명** 승인.
- 작성자는 PR 전에 별도 세션에서 `/code-review`·`/security-review`로 자가 검증한다(생성자 ≠ 검증자, [ai-code-trust.md](ai-code-trust.md)).
- 리뷰어는 전체 diff보다 **본문의 수용 기준·실행 방법**을 먼저 보고, 직접 실행해 확인한다. 필요하면 `gh pr diff <번호>`.
